SGLANG · LMCACHE INTEGRATION

SGLang × LMCache 数据路径与调用图

基于当前 LMCRadixCache：默认 MP 模式通过独立 LMCache Server 管理缓存；IP 模式在 SGLang 进程内运行 LMCacheEngine。两条路径最终都将命中数据写入 SGLang Device KV Pool。

MP 默认 · IP 可选
一句话结论：从 SGLang Tree 的视角，LMCache 是直接恢复到 L1 Device KV；LMCache 自己可能在内部经过 CPU DRAM 和磁盘/远端 storage，但这些不是 SGLang HiCache 管理的 Host L2。

1. 总体方案与模式选择

LMCRadixCache.__init__() 根据 device 选择模式：CUDA 默认 MP，XPU 默认 IP。

SGLang Scheduler

match_prefix 查命中；init_load_back 分配 Device slots；请求结束触发 store_kv。

SGLang L1

k_pool / v_pool 是模型 GPU/XPU KV tensors；通过 slot_mapping 指定读写位置。

MP Connector（默认）

LMCacheMPConnector 连接独立 daemon；GPU KV 可通过 CUDA IPC/传输机制与 server 协作。

IP Connector

LMCacheLayerwiseConnector 在进程内持有 LMCacheEngine，按 layer 搬运。

LMCache ConnectorMP: ZMQ/daemon；IP: in-process engine。

可选持久化层磁盘、远端、NIXL、Mooncake、S3 等 backend。

Load 终点

不论数据来自 LMCache CPU 还是远端，最终通过 connector scatter 到 slot_mapping 指定的 SGLang Device KV Pool。

Store 起点

SGLang 将 token_ids + kv_indices 交给 connector，由 LMCache 从 Device KV gather，再写入其内部缓存层。

LoadMetadata

token_ids

生成 chunk/object keys，决定查询哪个逻辑前缀。

slot_mapping

决定命中 KV 最终写到 SGLang Device Pool 的哪些 token slots。

offset / prefix_pad

处理已有 Device prefix 与 LMCache chunk 对齐，避免覆盖已命中 slots。

边界：LMCache 内部 CPU/storage 是否实际启用取决于运行模式与配置；“LMCache 直达 L1”描述的是 SGLang 集成接口的最终落点，并不代表网络/存储传输过程中绝不使用 CPU staging。
