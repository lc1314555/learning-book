◆1. 一张总览图

SGLang 是「前端 TokenizerManager → 每 TP/DP rank 一个 Scheduler（内含 TpModelWorker 与模型）→ DetokenizerManager」的进程结构，进程间用 ZMQ 传消息。KV 走 HiCache 三层：L1 Device KV 池、L2 HostKVCache（CPU 内存）、L3 HiCacheStorage（UCM）。

前端 橙=TokenizerManager；执行 紫=Scheduler/TpModelWorker；分层 蓝=HiCache L1/L2；L3 绿=UCM Store。

◆2. 调度主流程

关键点：调度（组 batch + 缓存命中 + 显存校验）全在 Scheduler 的事件循环里完成；模型执行由它同步驱动的 TpModelWorker 承担；输出经 Detokenizer 回到前端。

◆3. 请求生命周期（Req）

请求进入后先落到 waiting_queue，被调度进 batch 后成为 running；显存不足时可能被 retract 退回等待。核心数据是 Req 与 ScheduleBatch。

stateDiagram-v2 [*] --> WAITING WAITING --> RUNNING: 被调度进入 batch RUNNING --> RUNNING: decode 逐步生成 token RUNNING --> RETRACTED: 显存不足 retract_decode RETRACTED --> WAITING: 释放后重新入队 RUNNING --> FINISHED: 命中停止条件或达最大长度 FINISHED --> [*]

锚点：schedule_batch.py:1050 Req、:2447 ScheduleBatch；组批 :2839 prepare_for_extend / :3685 prepare_for_decode。

◆4. 前缀缓存命中如何缩短 prefill（重点）

核心机制：每个候选请求组批前先做 RadixCache.match_prefix，命中的 token 无需重算——prefix_lens 变大、extend_lens 变小，prefill 只处理未命中后缀。这是 SGLang 高缓存命中率的关键。
flowchart LR A["waiting_queue 候选 Req"] --> B["init_next_round_input"] B --> C["match_kv_cache 调 tree_cache.match_prefix"] C --> D["得到 prefix_len 与命中节点"] D --> E["prepare_for_extend 只填充未命中后缀"] E --> F["alloc_for_extend 写 KV 索引"]

锚点：common.py:220 match_kv_cache、radix_cache.py:364 match_prefix、allocation.py:374 alloc_for_extend。

◆5. 显存不足与 retract

检测

退让

◆6. 数据传输：L1 / L2 / L3（HiCache）

命名澄清：SGLang 用 HiCache 表达分层缓存，代码里是 Device KV pool（L1）、HostKVCache（L2，CPU）、HiCacheStorage（L3，外部）。UCM 实现的正是 HiCacheStorage 这个 L3 接口。

6.1 L1↔L2（Device ↔ Host）

L2TransferEngine 提交 Device→Host 备份 / Host→Device 回载；实际搬运由 HostKVCache.backup_from_device_all_layer / load_to_device_per_layer 完成。

6.2 L2↔L3（Host ↔ Storage）

HiCacheController 用后台线程驱动：写回（prefetch/write_storage）、淘汰（evict_host）。真正落到外部存储走 HiCacheStorage 的 batch_get_v1/batch_set_v1（零拷贝）或 v2 池接口。

◆7. L3 = UCM 适配详解

UCM 以 UnifiedCacheStore(HiCacheStorage) 接入 SGLang 的 L3 接口，内部委托给 SglangUcmConnector，最终调用 UCM 的 UcmKVStoreBaseV1.lookup / load_data / dump_data。粒度是 page（一页一对象；非 MLA 为 K/V 两个载荷，MLA 为单载荷）。

◆8. 端到端案例：命中 L2/L3 的请求

请求的 prompt 前段此前已被缓存：GPU 未命中，但 L2/L3 有对应 page，可回载后只算未命中后缀。

sequenceDiagram autonumber participant R as 新请求 participant S as Scheduler participant RC as RadixCache participant HC as HiCacheController participant UC as UCM R->>S: 入 waiting_queue S->>RC: match_prefix RC-->>S: GPU 命中 0 但 Host 命中若干 page S->>HC: ready_to_load_host_cache HC->>UC: batch_get_v1 回载命中 page Note over S: prefill 只计算未命中部分 S->>S: run_batch 执行并采样 S->>HC: flush_pending_backups HC->>UC: batch_set_v1 新 KV 落盘 S-->>R: 流式输出 token
收益与代价：命中把「重算 prefill」变成「回载 KV」，用存储/带宽换算力；代价是回载延迟，因此需靠 HiCacheController 的预取与写回策略平衡。op 级 wait 使当前 UCM 路径表现为同步——Direct Linker 会改为异步任务队列。

◆9. 进程与角色关系：UCM 在哪里

一句话：UCM 不是独立进程，也不自带调度器/执行器。它是以库的形式被引擎 import，在引擎已有的进程内运行，复用引擎的 Scheduler 与 Worker，只通过引擎提供的接口挂进去——SGLang 是 HiCacheStorage，vLLM 是 KVConnectorBase_V1。
flowchart TB subgraph P1["前端进程 TokenizerManager"] TM["HTTP 接收与分发"] end subgraph P2["Scheduler 进程 每个 TP rank 一个"] SCH["Scheduler 事件循环与组批"] WK["TpModelWorker 执行 forward"] HC["HiCacheController 线程 prefetch 与 backup"] subgraph UCMP["UCM 同进程库"] US["UnifiedCacheStore 实现 HiCacheStorage"] CS["UcmKVStoreBaseV1 store 与传输"] end SCH --> WK SCH --> HC HC --> US US --> CS end subgraph P3["DetokenizerManager 进程"] DET["detokenize"] end TM -.->|ZMQ| SCH SCH -.->|ZMQ| DET DET -.->|ZMQ| TM CS --> EXT["L3 外部存储 NFS 对象存储 等 独立部署"]
角色谁担任UCM 做什么
请求调度引擎 Scheduler不参与调度，仅被回调查命中、给出 block 计划
模型执行引擎 TpModelWorker / ModelRunner不参与 forward，仅在前后搬运 KV
KV 搬运UCM（同进程库）提供 lookup / load_data / dump_data

UCM 自己拥有的是进程内的线程与资源（IO 线程池、传输引擎、任务队列），而非独立服务：ucm/integration/sglang/unifiedcache_store.py:19；宿主控制线程在 cache_controller.py:457。

vLLM 侧同理

vLLM 的 connector 只有 SCHEDULER / WORKER 两个角色（KVConnectorRole），不是两个进程。kv_role=kv_both 时引擎在 Scheduler 进程与 Worker 进程各创建一个 UCM connector 实例；调度与执行仍由 vLLM 的 Scheduler / Worker 负责。

base.py:139 KVConnectorRole factory.py:43 create_connector

唯一真正跨进程/跨机的是外部存储本身：NFS、对象存储、远端 peer 等是独立部署的服务；UCM 只是它们在本进程内的客户端。三个概念别混淆——引擎 Scheduler（决定跑什么）、引擎 Worker（执行 forward）、UCM（同进程的 KV 存储/传输后端）。
