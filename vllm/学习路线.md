# vLLM 与 vLLM Ascend：调度流程和数据传输学习路线

本文基于本地 `C:\github项目\vllm` 和 `C:\github项目\vllm-ascend` 的代码布局整理。阅读顺序为：**vLLM 主调度闭环 → Ascend 执行接入 → KV 数据传输 → 多卡通信**。

代码路径均相对于对应仓库根目录。具体实现由运行配置决定，后续代码更新可能改变方法位置。

## 1. 整体关系与主调用链

vLLM 提供请求管理、调度和执行框架；vllm-ascend 通过硬件插件接入 NPU Worker、ModelRunner、通信和缓存传输实现。Ascend 也提供定制调度器，是否启用取决于配置。

```text
请求进入
  → AsyncLLM / EngineCoreClient
  → EngineCore 接收请求
  → Scheduler.schedule()
  → SchedulerOutput
  → Executor
  → Worker
  → ModelRunner.execute_model() / sample_tokens()
  → ModelRunnerOutput
  → Scheduler.update_from_output()
  → 返回生成结果，并进入下一轮调度
```

首先阅读 `vllm/v1/engine/core.py` 的 `EngineCore.step()`。本地版本位于约 709 行，主干为：

```python
scheduler_output = self.scheduler.schedule(...)
future = self.model_executor.execute_model(scheduler_output, non_block=True)
# 等待执行结果，并按实际路径完成采样等操作
engine_core_outputs = self.scheduler.update_from_output(...)
```

先理解这个闭环，再深入组件。同文件的 `step_with_batch_queue()` 涉及批次排队与执行重叠，第二遍再读。

## 2. 调度流程阅读路线

以下文件均位于 vLLM 仓库。

| 顺序 | 文件与方法 | 要回答的问题 |
|---|---|---|
| 1 | `vllm/v1/request.py` | 请求保存哪些状态？如何记录已计算 token？何时等待、运行、结束？ |
| 2 | `vllm/v1/core/sched/scheduler.py`：`schedule()`，约 718 行 | 本轮选择哪些请求？每个请求计算多少 token？ |
| 3 | `vllm/v1/core/sched/output.py`：`SchedulerOutput`，约 238 行 | 调度器向执行端下发哪些信息？ |
| 4 | `vllm/v1/core/kv_cache_manager.py` | 如何查前缀命中、分配 KV block 和释放缓存？ |
| 5 | `vllm/v1/core/sched/scheduler.py`：`update_from_output()`，约 2327 行 | 如何利用采样结果更新请求、判断结束并释放资源？ |

阅读 `schedule()` 时重点追踪：

- `waiting`、`running` 队列之间的迁移。
- token 预算和请求的 `num_computed_tokens`。
- `get_computed_blocks()`：已有多少本地 KV 可以复用。
- `allocate_slots()`：本轮执行需要分配哪些缓存块。
- 缓存不足时的抢占与重算。
- 外部 KV 尚未加载完成时，请求如何等待。

调度粒度是本轮需要计算的 token 数量。Prefill 和 Decode 在这个框架内参与调度，请求通常经过多轮执行。

完成上述阅读后，再查看 `vllm/v1/core/sched/async_scheduler.py`，理解异步调度如何改变状态更新时机。

## 3. Ascend 接入与 NPU 执行路线

以下文件均位于 vllm-ascend 仓库。

1. `vllm_ascend/__init__.py`：查看平台及其他扩展如何注册。
2. `vllm_ascend/platform.py`：搜索 `worker_cls`、`scheduler_cls`、`use_v2_model_runner`，确认运行时选用的实现。
3. `vllm_ascend/worker/worker.py`：约 599 行附近根据配置选择 ModelRunner。
4. 跟进实际选中的 Runner：
   - V1：`vllm_ascend/worker/v1/model_runner.py`，`execute_model()` 约 2347 行。
   - V2：`vllm_ascend/worker/v2/model_runner.py`，`execute_model()` 约 645 行。

本地代码同时存在 V1、V2 ModelRunner，先确认配置再选择一条路线。Runner V2 与 vLLM V1 引擎属于不同层面的命名。

在 Runner 中追踪：

```text
SchedulerOutput
  → 更新请求和批次状态
  → 准备 input_ids、positions、block table、slot mapping
  → 构造 Attention 元数据
  → 模型 forward
  → 采样 token
  → ModelRunnerOutput
```

两个关键映射：

- **block table**：请求的逻辑 KV block 对应哪些物理缓存块。
- **slot mapping**：本轮 token 产生的 KV 应写入哪些物理位置。

这两个概念连接了调度器的缓存分配与 Attention 的实际缓存读写。结果结构可查看 vLLM 的 `vllm/v1/outputs.py` 中 `ModelRunnerOutput`。

## 4. 数据传输的三条路线

| 类型 | 典型内容 | 阅读入口 |
|---|---|---|
| 引擎与 Worker 之间 | 调度信息、执行结果、进程间消息 | vLLM：`vllm/v1/engine/core_client.py`、`vllm/v1/executor/multiproc_executor.py` |
| KV 缓存传输 | P/D 分离、远端缓存、缓存卸载 | vLLM 的 KVConnector 接口与 Ascend Connector 实现 |
| 模型多卡通信 | TP 集合通信、PP 中间激活、MoE 通信 | vLLM：`vllm/distributed/parallel_state.py`；Ascend：`vllm_ascend/distributed/device_communicators/npu_communicator.py` |

`SchedulerOutput` 主要描述执行计划和元数据；KV tensor 的实际搬运由执行端及传输后端完成。

阅读 Executor 时，可先看 `vllm/v1/executor/uniproc_executor.py` 理解简单路径，再看 `multiproc_executor.py` 理解多进程分发。

## 5. KV 传输：先读接口，再选实现

首先阅读 vLLM 的：

`vllm/distributed/kv_transfer/kv_connector/v1/base.py`

将 `KVConnectorBase_V1` 的接口按调度侧和 Worker 侧理解：

| 调度侧：决定传什么 | Worker 侧：执行传输 |
|---|---|
| `get_num_new_matched_tokens()`：查询外部缓存命中 | `register_kv_caches()`：注册缓存内存 |
| `update_state_after_alloc()`：记录分配后的目标块 | `start_load_kv()`：启动加载 |
| `build_connector_meta()`：生成传输元数据 | `wait_for_layer_load()`：等待本层可用 |
| `update_connector_output()`：接收传输反馈 | `save_kv_layer()`：保存或发送本层 KV |
| `request_finished()`：处理结束后的缓存生命周期 | `get_finished()` / `get_transfer_results()`：反馈完成状态 |

这些是接口约定，各 Connector 的实现方式不同，部分钩子可能为空操作。调度侧与 Worker 侧也应区分于 Prefill、Decode 的生产者和消费者角色。

接着阅读 vLLM 的 `vllm/v1/worker/kv_connector_model_runner_mixin.py`，观察元数据绑定、启动加载、等待保存和收集结果如何串联。V2 路径还应对照 Ascend 的 `vllm_ascend/worker/v2/kv_connector.py`。

### 5.1 P/D 分离：Mooncake 路线

从 Ascend 仓库的以下目录开始：

```text
vllm_ascend/distributed/kv_transfer/
  kv_p2p/mooncake/connector.py
    → pull_scheduler.py
    → pull_worker.py
    → base_worker.py
  utils/mooncake_transfer_engine.py
```

重点追踪：

- 远端请求如何标识。
- 源端和目标端的 block 如何映射。
- 内存如何注册，地址如何交给传输后端。
- 何时发起传输，如何检测完成。
- 加载完成后，调度器何时允许 Decode。
- 请求结束后，正在传输的 block 何时可以释放。

先读 Pull 路径，再按实际使用情况扩展到 Push 或 layerwise 路径。

## 6. 第一轮最短阅读顺序

1. `EngineCore.step()`：掌握一次调度闭环。
2. `Scheduler.schedule()`：理解选择请求、分配 token 预算和 KV block。
3. `SchedulerOutput`：理解执行计划。
4. Ascend `Worker → ModelRunner.execute_model()`：理解计划如何执行。
5. `Scheduler.update_from_output()`：理解结果如何推动下一轮。
6. `KVConnectorBase_V1 → Mooncake 或 UCM`：补上外部 KV 加载和完成反馈。
7. 按需求继续阅读多进程 Executor、异步调度和多卡通信。

## 7. 用一个请求贯穿阅读

使用“输入 100 个 token、生成 3 个 token”的请求作为例子。先假设无前缀命中、无外部 KV，再加入缓存复用或远端加载。

逐轮记录：

| 观察项 | 需要记录的内容 |
|---|---|
| 请求状态 | waiting、running、等待 KV、结束等状态变化 |
| 已计算量 | `num_computed_tokens` 的变化 |
| 本轮计算量 | 本轮给该请求分配多少 token，为什么 |
| 缓存位置 | block IDs、block table、slot mapping |
| 执行结果 | 新生成 token、停止条件 |
| 传输状态 | 外部命中数量、加载是否完成、是否可释放缓存 |

具体每轮 token 数和时间点受 chunked prefill、异步调度等配置影响，以实际代码路径为准。最终应能解释：请求为什么在这一轮被选中、KV 位于何处、由谁搬运、执行完成后由谁更新状态。
